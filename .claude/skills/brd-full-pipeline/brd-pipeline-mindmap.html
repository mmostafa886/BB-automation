⚙️ Phase 0 — Setup & Workspace Configuration Setup ▼

Workspace Initialization

Auto-invoked Ensures required directory structure exists

What it does:

  • Extracts feature name from BRD (e.g., "Add Employee" → "Add_Employee")
  • Derives naming tokens:
    • FeatureName — underscored (Add_Employee)
    • EntityName — PascalCase entity only (Employee)
    • feature-slug — lowercase-hyphenated (add-employee)
    • page-kebab — entity in kebab-case (employee)
    • branch-name — feature/Add_Employee
  • Checks if required directories exist (stories/, test_cases/, src/pages/, tests/generated/)
  • If any directory is missing, invokes /Setup_Workspace skill
# Directory Structure Created stories/ # User Stories (.md files) test_cases/ # Manual Test Cases (.md files) src/ ├── locators/ # Self-healing locator definitions └── pages/ # Page Object Model classes tests/ └── generated/ # Playwright test specs └── <EntityName>/ # Organized by entity
🔧 Setup_Workspace Skill: Non-destructive operation — never deletes or overwrites existing files. Only creates missing directories.

📝 Phase 1 — BRD → User Stories (Product Owner) Phase 1 ▼

BRD_To_USs — ProductOwnerSkill

Input: BRD Text Output: User Stories

Expert Role: Agile Product Owner

  • INVEST Principle: Every story is Independent, Negotiable, Valuable, Estimable, Small, Testable
  • Atomic Stories: One story per flow — complex features broken into separate stories
  • Coverage: At least one Happy Path and one Unhappy Path per feature area
  • No Code: Pure business logic and user flows only

Output Format:

### [US_NN] US-<FeatureName>-<TitleSlug>: <Full Title in Title Case> **As a** [user persona], **I want to** [perform an action], **So that** [achieve a goal/value]. **Acceptance Criteria:** * **AC1:** [Criteria 1 — happy path] * **AC2:** [Criteria 2 — validation] * **AC3:** [Criteria 3 — edge cases/error handling] # Example: ### [US_01] US-Add_Employee-Add_New_Employee_Record: Add a New Employee Record **As a** HR Administrator, **I want to** add a new employee record to the system, **So that** I can maintain an up-to-date employee database. **Acceptance Criteria:** * **AC1:** System accepts valid employee data and creates record * **AC2:** System validates required fields before submission * **AC3:** System prevents duplicate employee IDs
Artifact Path Status

✅ Phase 2 — User Stories → Test Cases (QA Analyst) Phase 2 ▼

USs_To_TCs — QAAnalystSkill

Input: User Stories Output: Test Cases

Expert Role: Senior QA Analyst

  • Explicit Steps: Exact field names, exact data values, exact URLs
  • Single Verification: One test case verifies exactly one outcome
  • Full Traceability: Every test case traces back to specific AC (AC1, AC2, ...)
  • Multiple Test Types: Positive, Negative, Boundary, Security

Test Case ID Structure:

Format: USnn-TCnn-<TitleSlug>: <Full Title> USnn = Parent User Story sequential ID (US01, US02...) TCnn = Test Case sequential ID across ALL TCs (TC01, TC10...) TitleSlug = 3-5 key words: qualifier + subject Qualifier matches test type: - Valid (Positive tests) - Invalid (Negative tests) - Missing (Negative — required fields) - Duplicate (Negative — uniqueness) - Boundary (Edge values) - Unauthorized (Security) Example: US01-TC01-Valid_Employee_Creation: Valid Employee Creation with All Required Fields US01-TC02-Missing_Required_First_Name: Employee Creation Fails with Missing First Name US01-TC03-Boundary_Max_Length_First_Name: First Name at Maximum 50 Character Limit

Output Format:

### Story: US-Add_Employee-Add_New_Employee_Record **Test Case ID:** US01-TC01-Valid_Employee_Creation: Valid Employee Creation with All Required Fields **Type:** Positive **Preconditions:** User logged in as HR Admin; on Add Employee page **Steps:** 1. Navigate to /employees/add 2. Enter 'John' in the First Name field 3. Enter 'Doe' in the Last Name field 4. Enter '12345' in the Employee ID field 5. Click the 'Save' button **Expected Result:** System displays success message "Employee created successfully" and redirects to employee list showing new record

🤖 Phase 3 — Test Cases → Playwright Scripts (Automation Engineer) Phase 3 ▼

TCs_To_PLScript — AutomationEngineerSkill

Input: Test Cases Output: Playwright Scripts

Expert Role: Lead QA Automation Engineer

  • Self-Healing Architecture: 3-phase locator healing (Primary → Semantic → AI)
  • 4-Layer Output: Locators, Page Objects, POM Registration, Test Specs
  • Best Practices: Page Object Model, fixture pattern, web-first assertions
  • Smart File Naming: ADO ID mapping, stale file detection with git mv
⚠️ Pipeline Behavior: When invoked from BRD_Full_Pipeline, the skill:
  • ✅ Generates all 4 layers of code
  • ✅ Saves files to disk
  • ❌ Does NOT run tests (--execute-tests skipped)
  • ❌ Does NOT create PR
  • ➡️ Returns control to pipeline for Polish phase

4-Layer Architecture:

Layer File Path Purpose
1. Locators src/locators/<page-kebab>-page-locators.ts Self-healing locator definitions (3-phase: primary → semantic → AI)
2. Page Class src/pages/<page-kebab>-page-self-healing.ts Page Object Model extending SelfHealingPageBase
3. POM Registry src/pages/pom-lazy-self-healing.ts Updated in-place with new page registration
4. Test Specs tests/generated/<EntityName>/us<nn>-tc<nn>-<title-slug>.spec.ts One spec per test case using test.fixme()

Spec File Naming Logic:

Format: tc-<id>-<title-slug>.spec.ts <id> resolution priority: 1. ADO numeric ID from mapping file (TC-Boundary_Max_Length → 382) 2. Numeric TC ID strip prefix (TC-3914 → 3914) 3. Text fallback lowercase-hyphenated (TC-Valid_Admin_PIM → tc-valid-admin-pim) Examples: tc-3914-verify-reagents-page-not-accessible.spec.ts tc-382-boundary-max-length-enter-first-name-at-maximum.spec.ts tc-valid-admin-pim-navigation-valid-admin-navigation.spec.ts # Stale file handling (MANDATORY): Existing file with same title-slug → git mv to <name>_old.spec.ts Then write fresh spec

Key Architecture Rules:

  • SelfHealingLocator.from() — Every element gets 3-phase healing
  • SelfHealingPageBase — All pages extend base class
  • this.actions.* / this.assert.* — No bare page.* calls
  • selfHealingFixture — Specs access pages via pomSelfHealing.<page>
  • test.fixme() — All generated specs marked as pending by default
  • TC tags in title: TC-<id>: <Title> @P<priority> @<Module>
# Example Generated Spec Structure import { test } from '../../fixtures/self-healing-fixture'; test.describe('Employee Management - Add Employee', () => { test.fixme('TC-3914: Valid Employee Creation @P1 @Employee', async ({ pomSelfHealing }) => { // Access page via fixture await pomSelfHealing.employeePage.navigateToAddEmployee(); // All actions through page methods (no direct page.* calls) await pomSelfHealing.employeePage.fillFirstName('John'); await pomSelfHealing.employeePage.fillLastName('Doe'); await pomSelfHealing.employeePage.clickSaveButton(); // Web-first assertions through helpers await pomSelfHealing.employeePage.verifySuccessMessage('Employee created successfully'); }); });
✨ Phase 3.5 — Polish Generated Code (Quality Pass) Phase 3.5 ▼

Polish_Generated_Code

Auto-invoked In-place fixes

⚡ Auto-continues: Immediately invoked after Phase 3 completes, before git operations. Scoped to only the files created/modified in this pipeline run.

Four Quality Tasks (Execution Order):

Task 1 — Stray Backslash Removal (Test Specs)

Fixes extraneous backslash-escapes before opening quotes

# BEFORE (broken) test.describe(\'Title', () => { searchByKeyword(\'ID'); # AFTER (fixed) test.describe('Title', () => { searchByKeyword('ID');

Task 4 — Missing Method Scaffolding

Detects methods called in tests but not implemented in page classes

# Test calls non-existent method: await pomSelfHealing.productsPage.verifySearchResultsDisplayed(); # Stub auto-generated in ProductsPageSelfHealing: /** * @generated-stub Polish_Generated_Code Task 4 */ async verifySearchResultsDisplayed(): Promise<void> { throw new Error('Not implemented: verifySearchResultsDisplayed'); } # Near-duplicate methods create aliases instead: async verifyNoSearchResultsMessageDisplayed(): Promise<void> { await this.verifyNoResultsFoundMessageDisplayed(); }

Task 3 — Extract Inline Locators

Refactors inline locator expressions to self-healing architecture

# BEFORE (inline — no self-healing): const lotsTab = (await this.pageContainer.get()) .locator('[data-testid="lots-tab"]').first(); await this.actions.click(lotsTab, 'Click Lots tab'); # AFTER (repository — full 3-phase healing): await this.actions.click(await this.lotsTab.get(), 'Click Lots tab'); # Added to locator repository + SelfHealingLocator field + constructor wiring

Task 2 — Re-arrange Page Methods

Sorts methods into canonical layout

# Canonical Order: 1. Navigation methods (navigateTo*, goto*) 2. Action methods (click*, fill*, select*, search*, get*Data) 3. Assertion methods (verify*, assert*) 4. Combined methods (methods using both actions + assertions) # Alphabetical within each section # Removes dead generation comments
