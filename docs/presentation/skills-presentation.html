Part 1: What Are Claude Code SKILLS?

What Are Claude Code SKILLS?

SKILLS are reusable, named AI workflow modules stored as Markdown files in .claude/skills/

Invoked with /skill-name in Claude Code chat

Each skill encodes:

  • Expert instructions (multi-step workflow)
  • Tool permissions (Bash, Edit, Write, Grep, APIs)
  • Auto-chaining logic (one skill triggers the next)
  • External integrations (Jira, Playwright MCP)

Think of them as plugins or macros for intelligent test automation

SKILLS bridge the gap between prompts (one-shot) and scripts (fixed steps). They're designed for complex, multi-step workflows that need to adapt to the environment.

Anatomy of a SKILL File

---
name: tcs-to-plscript
description: Manual Test Cases → Playwright specs
type: content generator + TAF builder
tools: [Bash, Write, Edit, Read, Grep]
---

# Step 1: Parse test case markdown
Read the TC file, extract scenarios...

# Step 2: Generate locators
Create src/locators/<page>-locators.ts

# Step 3: Generate page objects
Create src/pages/<page>-page-self-healing.ts

# Auto-chains into:
/polish-generated-code
Each SKILL is a markdown file with a YAML frontmatter header. The header declares the skill's name, what tools it uses, and what it chains into.

SKILLS vs. Prompts vs. Scripts vs. Cursor Rules

Aspect SKILLS Prompt Script Cursor Rules
Where .claude/skills/ Chat input filesystem .cursor/rules/
Execution Agentic One-shot OS shell Manual steps
Tool access Full None OS only Limited
Auto-chain ✅ Yes ❌ No ❌ No ❌ No
SKILLS are unique because they combine the intelligence of LLMs with the reproducibility of scripts, plus automatic chaining.

The 4-Layer TAF Architecture

Layer 1: LOCATORS
└─ src/locators/<page>-page-locators.ts
   Pure selector data (CSS, XPath, ARIA roles)

Layer 2: PAGE OBJECTS
└─ src/pages/<page>-page-self-healing.ts
   Action methods (click, fill, navigateTo)
   Assertion methods (assertVisible, assertHasText)

Layer 3: POM MANAGER
└─ src/pages/pom-lazy-self-healing.ts
   Lazy-initialized singleton for all pages

Layer 4: TEST SPECS
└─ tests/generated/<Module>/tc-*.spec.ts
   Call pomSelfHealing.<page>.<method>()
   No direct locator usage
Every test follows this strict 4-layer pattern. This separation keeps code clean and maintainable.

Auto-Chaining Pipeline Flow

TAF Migration:

scaffold → create-page-locators → create-selfhealing-page → register-page-in-pom → migrate-test-to-selfhealing → polish-generated-code

Content Generation:

brd-to-uss → uss-to-tcs → tcs-to-plscript → polish-generated-code

ADO-Native:

brd-to-uss → jira-uss-to-tcs → tcs-to-jira (+Test Plan)
jira-tcs-to-plscript → polish-generated-code

Each arrow = automatic chaining (no human input)

The beauty of auto-chaining is that you invoke one skill and the entire pipeline runs. For example, /brd-full-pipeline will parse the BRD, generate User Stories, generate Test Cases, generate Playwright specs, and polish them — all without you doing anything.

Business Value — BRD to Green Tests

  • BRD in, green tests out — no manual TC writing, no manual spec coding
  • Self-healing locators — 3-phase fallback: primary selector → semantic AI → full browser re-inspection
  • Bidirectional Jira — generate FROM ADO work items OR push TO ADO with full traceability
  • Zero manual locator hunting — extracted from specs, organized in repositories
  • Autonomous test repair — /execute-and-fix-tests inspects failures, fixes code, re-runs
The real value here is time savings and consistency. Teams don't have to manually write test cases or worry about maintaining brittle selectors.

Part 4: Agentic SKILLS

What Makes a SKILL "Agentic"?

Agentic = multi-step, autonomous, self-directed

Characteristics:

  • Spawns multiple sub-tasks without human approval
  • Adapts to environment state (checks for missing files, existing code)
  • Chains tools together (Bash → Edit → Grep → Write → repeat)
  • No user input needed between steps
  • Repairs its own mistakes

Example: /execute-and-fix-tests runs tests → inspects app → identifies failures → fixes code → re-runs — all without asking

Agentic skills are different from traditional scripts or prompts. They can reason about what they're doing and adjust their approach if something fails.

Agentic SKILLS in This Project (7 total)

  1. taf-full-pipeline — Detects progress, chains 6 skills sequentially
  2. brd-full-pipeline — PDF parsing → codegen → commit
  3. jira-full-pipeline — BRD → ADO work items + local artifacts
  4. execute-and-fix-tests — Autonomous run→inspect→fix→re-run loop with Playwright MCP
  5. jira-tcs-to-plscript — Fetches ADO data → generates TAF code
  6. analyze-trace — Parse trace.zip → classify failure → apply patch
  7. polish-generated-code — 5 code-quality passes
These 7 skills represent the most complex and valuable workflows in our toolkit. They handle the heavy lifting of test automation.

Part 5: Portability — Using SKILLS Elsewhere

Can We Use SKILLS in Other Tools?

Short answer: Not directly. SKILLS are Claude Code–native.

"If I move them to Cursor, would they work the same?"

No. The SKILLS would need to be rewritten as separate prompts or Cursor rules, and you'd lose:

  • Auto-chaining (each step is manual)
  • Full tool suite (no Bash/Edit/Write access)
  • ADO API integration (require scripts)
  • Agentic behavior (no step-by-step adaptation)
SKILLS are tightly integrated with the Claude Code runtime. While the concepts could be ported elsewhere, you'd lose a lot of the automatic behavior.

Named Portability Examples

Example 1: /execute-and-fix-tests in LangChain

agent = AgentExecutor(
  agent=Agent(tools=[PlaywrightBrowserTool(),
                     BashTool(), FileEditTool()]),
  llm=ChatOpenAI(model="gpt-4"),
)

Example 2: /jira-full-pipeline in CrewAI

crew = Crew(agents=[
  BRDAnalystAgent(), UserStoryWriterAgent(),
  TestCaseGeneratorAgent(), PlaywrightCoderAgent()
])

Key: The pattern is portable; the runtime is not.

If you really needed to port these elsewhere, you could use frameworks like LangChain or CrewAI, but it would require significant work to rebuild the tool integration.

Part 6: CI/CD Pipelines

Real Pipelines in This Project

Located in pipelines/ folder:

File Purpose Uses SKILLS?
azure-pipelines.yml PR/push → run tests → reports ❌ No
ai-generation.yml Manual: Stage1=/jira-full-pipeline, Stage2=/execute-and-fix-tests ✅ YES
execute-fix.yml On-demand /execute-and-fix-tests ✅ YES

Invocation:

printf '/ADO_Full_Pipeline\n%s' "$(cat $BRD_FILE)" \
  | claude --dangerously-skip-permissions -p
These are real, production pipelines running in Jira right now. They invoke SKILLS via the Claude CLI.

CI/CD Integration Patterns

Pattern 1: AI Generation Gate (ai-generation.yml Stage 1)

New BRD → /jira-full-pipeline → generates US, TCs, scripts → pushes branch

Pattern 2: On-Demand Test Fix (execute-fix.yml)

Developer queues pipeline → Claude fixes failing tests autonomously

Pattern 3: Classic Playwright (azure-pipelines.yml)

PR trigger → run area-filtered tests → publish reports

Important clarification on --dangerously-skip-permissions:

Safe in CI because pipelines run in ephemeral Ubuntu VMs that are destroyed after the job. On your local machine, this flag would be genuinely dangerous.

The first two patterns directly use SKILLS. The third is a traditional Playwright run. All three complement each other in a complete CI/CD strategy.

Part 7: Optimizations & Roadmap

Current Gaps & Solutions

Gaps:

  • pipeline-guard stub → pre-merge validation gate
  • token-cost-tracker stub → log token usage per skill
  • Sequential chaining → parallelize independent skills
  • No deduplication → auto-run /merge-tc-sets after TC generation

Performance:

  • Snapshot-based healing: cache DOM → faster Phase 3 healing
  • Enable commented-out push step in ai-generation.yml for hands-free BRD→PR
These are opportunities we can tackle in future sprints to make the system even more powerful and cost-effective.

Roadmap Ideas

  • ADO Dashboard — live pass/fail mapped to work items
  • Multi-env skills — test vs. staging ENV switching
  • API Contract Layer — OpenAPI spec → API test cases
  • SKILL Versioning — semver tags in frontmatter
  • Snapshot Registry — store last-good DOM snapshots per locator
These are longer-term ideas to build on the foundation we have. Each would add significant value.
