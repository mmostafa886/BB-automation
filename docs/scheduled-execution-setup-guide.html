Scheduled Execution — Setup Guide

One-time manual configuration required for .github/workflows/scheduled-execution.yml to run correctly: the Slack webhook secret, GitHub Pages hosting for historical reports, and workflow permissions. None of this can be done by editing files — it all lives in repository settings.

·Overview

The scheduled workflow (renamed from signup-scheduled-tests.yml to scheduled-execution.yml, since more modules will be added to it over time) now does three additional things after the tests finish:

  • Publishes the Playwright HTML report to the gh-pages branch under reports/<run_number>/, keeping every previous run's report intact (keep_files: true) — in addition to, not instead of, the existing per-run artifact upload.
  • Writes the report URL to the job's step summary.
  • Posts a pass/fail message to Slack via an Incoming Webhook, with links to both the Actions run and the published report.

It also now runs weekly (Friday 00:00 UTC, was daily) and can be triggered manually via workflow_dispatch instead of only on the cron schedule.

Why an Incoming Webhook, not a Slack Bot/API? A webhook needs exactly one repository secret and a single curl call. The bot/API route (slackapi/slack-github-action, a bot token, app installation, OAuth scopes, channel ID lookup) is built for rich, interactive messages — nothing this pass/fail ping needs. It would add setup steps without adding capability actually used here.

1Create the Slack webhook secret

In Slack:

  1. Go to api.slack.com/apps → Create New App → From scratch. Name it (e.g. "BB Automation Notifier") and pick the workspace.
  2. In the app's settings, open Incoming Webhooks and toggle it On.
  3. Click Add New Webhook to Workspace, choose the channel that should receive scheduled-run notifications, and authorize.
  4. Copy the generated webhook URL (https://hooks.slack.com/services/…) — it's shown once and can be regenerated later if lost.

In GitHub:

Repo→Settings→ Secrets and variables→Actions→ New repository secret
  1. Name: SLACK_WEBHOOK_URL
  2. Value: the webhook URL copied above.
  3. Save.

2Enable GitHub Pages

Repo→Settings→ Pages
  1. Under Build and deployment, set Source to Deploy from a branch.
  2. Set Branch to gh-pages / /(root).
  3. Save.
The gh-pages branch doesn't need to exist yet. The peaceiris/actions-gh-pages action creates it automatically on the first successful run. If the branch selector doesn't show gh-pages yet, run the workflow once first (see Step 4), then come back and finish this step.
Private repos: GitHub Pages hosting for a private repository requires GitHub Pro, Team, or Enterprise. Public repositories get Pages for free. Check Settings → Pages — if the option is greyed out, this is why.

Once enabled, published reports will be reachable at:

https://<owner>.github.io/<repo>/reports/<run_number>/

3Confirm workflow permissions

The workflow file itself declares permissions: contents: write, which is normally sufficient on its own regardless of the repository-wide default. This step is only relevant if an organization-level policy hard-restricts what workflows are allowed to request.

Repo→Settings→ Actions→General→ Workflow permissions

Confirm this is not locked to a read-only default that an org policy prevents workflows from overriding. If the gh-pages push step fails with a permissions error despite the YAML declaration, this is the first place to check.

4Test it end to end

  1. Actions tab → Scheduled Execution → Run workflow (uses the new workflow_dispatch trigger — no need to wait for Friday).
  2. Watch the run: tests execute, both artifacts upload, the Publish report to GitHub Pages step succeeds.
  3. Open the run's Summary tab — it should show a "Playwright report" link.
  4. Follow that link; it should render the Playwright HTML report.
  5. Check the Slack channel — a message with a pass/fail status, a "View run" link, and a "View report" link should have arrived.
  6. Run the workflow a second time and confirm the first run's reports/<run_number>/ report is still reachable — this is what proves history isn't being wiped on each publish.

?Troubleshooting

SymptomLikely cause
Report URL 404s right after a run finishes GitHub Pages takes roughly a minute to rebuild after a push to gh-pages. Wait and retry.
Pages branch selector doesn't list gh-pages The branch is created by the first successful workflow run, not before. Run the workflow once, then revisit Settings → Pages.
Slack step fails (curl exits non-zero) SLACK_WEBHOOK_URL is missing, mistyped, or the webhook was revoked/regenerated in Slack. Re-check the secret value.
Publish report to GitHub Pages step fails with a permission/push error See Step 3 — an org-level policy may be preventing the workflow's contents: write permission from taking effect.
Pages shows a 404 for the whole site, not just one report GitHub Pages isn't enabled yet, or the repo is private without a plan that supports Pages. See Step 2.
